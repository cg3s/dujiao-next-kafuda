## 1. 交付目标

### 1.1 完整业务链路

管理员新增或编辑商品时可切换为「Kafuda GPT Direct（直充）」类型。切换后，后台从 Kafuda 动态读取套餐及可售地区生成 SKU；管理员为每个 SKU 自定义成本价和售价，启用后才可购买。该类型不使用卡密库存及人工库存逻辑。

买家选定规格并完成站内付款，再从订单详情按第 6.2 节待确认的协议完成充值授权。商城后端调用 Kafuda GPT 直充 API，页面自动反馈检查、提交、充值中及最终结果；上游确认充值完成后，商城订单自动同步为 `completed`（已完成）。出现履约异常时，订单自动转入人工交付处理，向买家展示人工处理中，由运营核对后处理。

自动充值链路不使用卡密。人工处理仅展示脱敏业务结果，若确需再次检查账号资格，由买家重新授权。

### 1.3 建议首期边界

- **购买范围：**只开放给主站已登录买家，每笔订单仅含一个直充规格、数量为 1，通过「立即购买」结算。
- **暂不开放：**游客、混合购物车、分销站、渠道 API 和下游站点；不改造已产生订单的旧商品，也不做自动退款。
- **商户付款：**首期建议用商户侧 `auto_card`，由运营配置可用的 `product_code`；`own_card` 留作后续能力。买家不选择或接触商户付款卡。
- **地区限制：**如果联调确认目标地区不支持该卡头，先停售对应规格。

## 2. 商品与动态 SKU

### 2.1 商品类型

在现有商品编辑弹窗与商品写入逻辑中增加独立的「Kafuda GPT Direct（直充）」选项，建议内部值 `fulfillment_type=kafuda_gpt_direct`。这是商品履约类型，和上游商户付款方式 `auto_card` / `own_card` 分别建模。

选中后展示目录同步、SKU 成本价、售价和启停控件，隐藏卡密导入、卡密库存、人工库存、库存展示配置和普通人工交付结算表单。不能因卡密数量为 0 而将直充 SKU 判为售罄；可售性由 SKU 配置、目录和运营开关决定。订单创建、取消、付款、退款均不执行卡密或人工库存预占、扣减、释放和回补。

切换类型时核查已有 SKU、卡密占用、上游映射与未完结订单，明确不兼容配置的处理提示，不自动删除已有卡密或改写历史订单快照。已产生订单继续按其原快照履约；本期不批量转换旧订单。异常转人工仅作用于对应订单的履约处理方式，不把商品或其他订单整体改为 `manual`。

正常直充单不能通过普通人工交付或通用改状态绕过上游确认。已进入人工处理的异常单，可经第 4.4 节的受控入口交付。

### 2.2 动态获取、站内定价

服务端调用 Kafuda `GET /api/v1/gpt/catalog`，用实际确认可售的「`plan` + `country`」作为同一商品下的规格键；不能仅凭套餐和地区列表做笛卡尔积。复用本地 SKU ID、规格和价格字段，另外保存明确的上游标识、目录可用状态。

新规格默认未完成价格配置、未启用；管理员按站内币种逐个自定义成本价与基础售价。复用 `ProductSKU.CostPriceAmount`（`cost_price_amount`）和 `PriceAmount`（`price_amount`），两项均由管理员维护，遵循现有金额精度与合法性校验。成本可显式配置为 0，不将缺失配置静默视为已确认；售价须满足现有可售校验。

区分三类金额：管理员成本价用于本地成本快照与利润口径；站内售价用于买家结算；上游报价和实际费用用于商户扣费及风控。上游约价只给运营参考，不能自动覆盖管理员成本价或售价，也不能直接替代 USD cents 的上游成本上限。实际扣费单独记录，不回写覆盖已下单的成本快照。成本、商户报价及实际费用仅对授权后台公开，买家接口和页面不得暴露。

首期沿用现有站内定价和支付校验，直充 SKU 的优惠配置须纳入上线检查。

### 2.3 同步规则

- 进入编辑页时读取最近一次有效目录，管理员可刷新。
- 按规格键合并，保留 SKU ID、管理员成本价、售价和手动启停；目录确认下架时停止新购，不删除 SKU；重新出现时保留两种价格，由管理员复核后重新开售。
- 目录请求失败或响应无效不覆盖上次有效数据；展示同步结果和时间，目录超过运营设定的有效期则暂停新购。
- 商品浏览和结算读取本地数据，预览与创建订单都重新校验可售性。

### 2.4 订单快照

创建订单时锁定本地 SKU、套餐、地区、管理员成本价、站内成交价及履约所需的付款配置标识（不含密钥）；复用订单项已有 `CostPrice` 成本快照，并检查买家响应的成本剥离逻辑。不接受买家在直充请求中覆盖这些字段。

后台修改成本价或售价、停售、刷新目录后，已付订单仍按快照处理；若上游已无法提供该规格，订单进入人工交付处理，不能悄悄换区、换套餐或补价。

### 2.5 前台展示

商品页显示套餐、地区、售价及付款后授权提示。把锁区、已有订阅、半价资格或点数资格等限制说明放在购买前；具体账号资格以付款后检查为准。可售按履约就绪、本地启用、定价及目录状态判断，不显示卡密库存数量，也不承诺账号一定能开通。

## 3. 支付后直充

### 3.1 等待授权

在线付款回调或钱包支付沿用商城现有逻辑。订单确认已付后，支付结果页引导到订单详情，等待买家完成授权。未付、取消、已退款及非本人的订单不能提交；服务端校验用户、租户和实际履约子单。支付成功本身不调用 Kafuda，也不触发自动发卡、人工发货或现有上游采购。

### 3.2 完成授权后检查并下单

- 买家核对已购套餐、地区和待充值账号，主动提交登录 Session；服务端只将其同步用于本次账号检查，不保存或放入后续创建订单请求。
- 服务端校验授权的用途和有效期，再按已确认的供应商协议检查账号资格。地区、`pay_mode` 和卡头以订单快照为准，只选与已购套餐相同、`available` 且未过期的一条报价。
- 锁区、已开通、无资格、暂不可买时提示原因并进入人工交付处理。授权无效或过期时允许买家重新授权；身份校验拒绝不改变订单状态。
- 报价有效期读 `expires_at`，不写死为九分钟。若检查回报的业务类型或费用超出商户允许范围，进入人工交付处理，商城不改变已付金额。

### 3.3 调用上游

调用 Kafuda `POST /api/v1/gpt/orders`，发送刚取得的 `quote_id` 与商户侧生成的唯一 `reference`，长度 1–80 字符。`auto_card` 用目录确认的卡头；后端按实际报价字段设 USD cents 的成本上限，包括开卡和充值成本；不直接用当地币金额与站内售价相减，也不直接把管理员填写的站内币种成本价当作上游限额。余额不足、卡头异常或超限时暂停本次提交，自动进入人工交付处理并提示运营。

### 3.4 查结果与实时进度反馈

受理后保存上游数字订单 ID。后台轮询 Kafuda `GET /api/v1/gpt/orders/{id}`，按接口建议的 5–10 秒起步，之后按限额、运行时长和错误退避；页面只读取站内状态。账单已付但上游未确认时保持处理中。

前台在订单详情自动轮询站内状态接口，展示「待提交 → 检查中 → 提交中 → 充值中 → 已完成 / 人工处理中」及最近更新时间，无需买家手动刷新。首期沿用站内鉴权请求与轮询方式，页面进入时立即拉取，离开时清理轮询，恢复页面时重新拉取；临时网络错误重试并提示同步延迟，不显示为充值失败。前后台都可看到最新的脱敏业务阶段。

进度仅展示接口确实可确认的阶段，不编造百分比、剩余时间或内部日志。上下游轮询周期分别配置并受限流约束，联调记录实际反馈延迟；这是近实时状态反馈。完成后停止页面轮询；人工处理中降低频率或按需刷新，结果不明时后台仍继续查证。页面离开不终止服务端履约任务。

上游确认 `completed` 后，幂等创建脱敏交付记录，履约状态记为已交付，实际履约订单状态直接同步为 `completed`（已完成）；存在父单时汇总更新父单，前台自动显示完成。不能只写成 `delivered` 后再等待人工完成。

回调有完整签名、重放防护、事件样例后再接入；校验通过的回调也走同一状态更新入口，必要时按订单 ID 主动查证。

### 3.5 直充状态与处理规则

| 直充子状态 | 处理规则 |
| --- | --- |
| 待提交 / 可更正 | 已付且无在途尝试；校验失败时显示可操作的提示。报价明确过期且确认未受理时，重新提交后获取新报价。 |
| 检查中 / 提交中 / 处理中 | 上游 `submitting`、`processing` 或站内正在处理；拒绝新增尝试，刷新页面可继续查看。 |
| 人工处理中 / 待核对 | 上游 `needs_review`，或提交超时等造成结果不明；自动进入人工队列并继续查单，必要时由运营用 `reference` 核对。禁止再次充值、人工标记完成和直接退款。进程重启本身优先恢复任务；恢复后仍无法确认结果才转待核对。 |
| 人工处理中 / 待人工交付 | 上游明确失败或取消、账号业务资格不符、费用超限等无法继续自动履约；记录脱敏原因。仅确认不会再自动开通且无在途尝试后，开放受控人工交付、重新提交或售后退款。 |
| 已开通 / 订单已完成 | 上游 `completed`；幂等落交付记录与时间，实际履约单设为 `completed` 并汇总父单，关闭该单人工待办。订单详情展示脱敏结果，不生成卡密文件；完成提醒不包含凭据。若接口返回 `renewal_cancelled`，按实际结果展示；点数不显示续费信息。 |
| 失败 / 已取消（上游尝试） | 上游尝试保留 `failed` 或 `cancelled` 结果；商城已付订单转人工交付处理，不因上游取消而改成未付或已退款。Kafuda 退商户服务费与商城买家退款是两笔业务。 |

### 3.6 异常转人工的状态语义

代码中的订单主状态（`paid`、`fulfilling`、`completed` 等）与交付类型（`auto`、`manual` 等）是两种概念，目前没有名为「人工交付」的订单主状态。本期须增加可持久化的订单人工接管标记 / 履约子状态，在前后台明确展示「人工处理中」，并支持后台筛选及待办；字段名称在 K02 规划时确定。

进入人工处理时，保留已付事实，未完成订单主状态使用 `fulfilling`，保留商品类型、原始订单快照、上游尝试和 reference；不能仅修改商品类型或显示文案来代替状态落库。人工处理原因区分「待核对」与「可人工交付」，异常发生后自动进入对应队列，不依赖用户主动联系客服。

普通查单的短暂网络失败按退避继续；达到配置的重试或处理时限后转人工待核对。结果不明转人工后继续上游查询；若随后确认成功，仍走统一幂等完成入口，并关闭人工交付操作。人工操作与上游结果更新使用相同订单锁，防止双方各交付一次。

### 4.2 凭据只用于当次请求

- 通过 HTTPS、带大小限制的 POST 请求体提交；前端仅置于表单内存，提交后清空。
- 后端只在检查/报价请求期间使用，不进人工表单、数据库、Redis、任务负载或重试队列；不进入 URL、日志、监控链路、埋点、错误报告及客服界面。
- 关闭该路由的请求体采集，也不透传上游原始错误或完整邮箱。订单仅公开脱敏账号与可公开状态。
- 对用户和订单限流；加载商户密钥使用部署侧敏感配置。

### 4.3 防重复充值

- 每个履约单任一时刻最多一个活跃尝试。先在短事务内锁定订单、核验可履约并持久化尝试号及唯一 `reference`；调用上游下单前先记录「可能已发出」，提交事务后才发请求。
- 并发点击、请求重放、进程重启和任务重投均复用已有记录。已知上游 ID 直接查单；拿不到 ID 时优先按 `reference` 查证。
- 只有上游明确支持安全重放且可复用原请求时，才用相同 `reference` 重放；不以新报价或新 reference 猜测重试。
- 若只有按数字 ID 查询且未收到 ID，转人工核对并保留原尝试。供应商的人工查单渠道记录在第 6.2 节。

### 4.4 人工交付、退款与状态一致

- 直充异常自动持久化人工处理标记、脱敏原因和进入时间；后台可筛选待核对、待人工交付及已处理。保留原始直充快照，不全局修改商品类型，不丢失上游尝试。
- 仅已进入人工队列、确认上游不会再开通且无在途尝试的订单可人工交付。运营确认实际完成后，经受权限控制的入口记录脱敏交付结果和操作人；本期直充异常单人工交付后也进入 `completed`，不改变普通人工商品原有流程，不导入、预占或生成卡密。
- 如需恢复自动直充，由运营先核实并解除人工接管；买家重新授权后才可开启新尝试，不从任务或数据库中恢复旧凭据。待核对期间始终禁止重充。
- 提交、人工接管、人工交付、上游结果更新和退款使用同一订单锁并在事务内复核状态。已退款不允许提交；提交中、处理中与结果不明不允许退款；上游成功与商城退款不能互相覆盖。后台普通人工交付和通用状态更新入口同样执行这些约束，不能绕过专用界面限制。
- 确认未开通且无在途尝试后，由现有售后流程根据站内实付发起退款，不以 Kafuda 退费作为买家退款凭证。
- 回调、轮询及人工处理的同一结果只产生一次交付和完成通知；迟到的成功关闭人工待办，旧事件不能把已完成订单退回人工处理中。

### 4.5 任务及事务

- 协调状态与到期任务持久化；建议首期复用现有 Redis worker，并用周期扫描补偿漏入队和重启。任务只传本地记录 ID。
- 销售开关开启时仍需校验 worker 已配置且运行。提供管理员按已知上游 ID 核对的入口，处理已付款订单。
- SQLite 事务内只用绑定 store，设置事务外预读，HTTP 调用全部在事务外；迁移及并发行为兼容 SQLite 和 PostgreSQL。

打开 <http://127.0.0.1:5179/>。演练预置 Plus 菲律宾规格和 200 CNY 测试余额，每笔订单为 100 CNY。先预览并用演练钱包付款，再选择成功开通或转人工核对，点击「授权模拟履约」和「推进模拟查单」查看订单进度。

演练服务默认使用独立内存 SQLite，只监听本机回环地址。端口占用时可以在命令末尾追加 `-kafuda-rehearsal-port=5180`。按 `Ctrl+C` 停止，重启即恢复测试余额和初始数据。

使用 PostgreSQL 时，将 `TEST_POSTGRES_DSN` 设为允许创建 schema 的测试库连接，并在演练命令末尾追加 `-kafuda-rehearsal-postgres`。每次运行创建独立 schema，按 `Ctrl+C` 正常停止后自动清理。设置该环境变量也会让 `TestDirectBuyerFlowRehearsal` 和 `TestDirectBuyerOnlinePaymentRehearsal` 在 SQLite 之外使用 PostgreSQL 运行相同回归。

#### 使用 Classic 或 Vault 店面演练

按第 7.2 节在 `frontend/user/` 运行 `pnpm run build`。演练使用同源 API，构建时将 `VITE_API_BASE_URL` 留空。构建后返回仓库根目录。

```powershell
$storefrontDir = (Resolve-Path frontend/user/dist).Path
go test -v -timeout 0 -run '^TestServeDirectBuyerRehearsal$' ./internal/modules/order/integrationtest/rehearsal -args -kafuda-rehearsal "-kafuda-rehearsal-storefront-dir=$storefrontDir"
```

打开 <http://127.0.0.1:5179/rehearsal>，点击「打开 Classic 店面」或「打开 Vault 店面」，以演练买家进入商品页。选择规格并点击「立即购买」，用演练钱包完成结算。

验证买家授权表单时，在已付订单详情提交合成 Session `local-rehearsal-session`，演练上游直接返回充值完成。

在订单详情复制已付订单号，并保留该标签页。另开演练页，填写订单号并点击「读取店面订单」。选择本次结果，点击「授权模拟履约」，再点击「推进模拟查单」。切回原订单详情即可看到自动更新的进度。此模式的店面和真实商城 HTTP 路由使用相同的回环来源，授权与上游结果由演练页模拟。

#### 演练续费结果与点数展示

在店面演练命令末尾追加 `-kafuda-rehearsal-renewal-cancelled=true` 或 `-kafuda-rehearsal-renewal-cancelled=false`，并在演练页选择「成功开通」，可查看 Plus 订阅完成后的两种续费提示。省略该参数时订阅详情隐藏续费提示。

追加 `-kafuda-rehearsal-product=gpt_credits` 可切换到 Codex 250 点数规格。使用相同付款和履约步骤，点数单完成后仅显示充值进度与交付状态。

#### 演练线上支付回跳

在上述命令末尾追加 `-kafuda-rehearsal-online`。进入店面后选择「模拟线上支付」并提交订单，保持「优先使用余额支付」未选中。模拟收银台会回到商城支付页，订单此时仍待支付。

保留支付页并复制订单号，另开演练页，填写订单号后点击「读取店面订单」和「确认模拟入账」。商城验证本地签名回调并入账后，支付页会自动进入订单详情。可继续通过演练页的「授权模拟履约」和「推进模拟查单」查看最终状态。渠道密钥由演练进程生成，订单、钱包和支付记录存于本次运行的内存 SQLite 或独立的 PostgreSQL schema。

#### 演练客服人工交付

在 `frontend/admin/` 运行 `pnpm run build:fullstack`。保留已构建的店面产物，回到仓库根目录启动同一个演练服务。

```powershell
$storefrontDir = (Resolve-Path frontend/user/dist).Path
$adminDir = (Resolve-Path frontend/admin/dist).Path
go test -v -timeout 0 -run '^TestServeDirectBuyerRehearsal$' ./internal/modules/order/integrationtest/rehearsal -args -kafuda-rehearsal "-kafuda-rehearsal-storefront-dir=$storefrontDir" "-kafuda-rehearsal-admin-dir=$adminDir"
```

用店面创建已付订单，在演练页读取该订单，选择「上游确认未开通」，再点击「授权模拟履约」和「推进模拟查单」。买家详情进入人工核对。在演练页点击「打开客服后台」，使用预置客服账号筛选「待直充核对」，进入订单详情并确认「记录人工交付完成」。切回买家订单详情可看到自动更新的完成状态。
