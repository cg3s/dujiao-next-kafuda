## 1. 交付目标

### 1.1 完整业务链路

管理员新增或编辑商品时可切换为「Kafuda GPT Direct（直充）」类型。切换后，后台从 Kafuda 动态读取套餐及可售地区生成 SKU；管理员为每个 SKU 自定义成本价和售价，启用后才可购买。该类型不使用卡密库存及人工库存逻辑。

买家选定规格并完成站内付款，在订单详情填写自己的 ChatGPT Session 并确认直充。商城后端直接调用 Kafuda GPT 直充 API，页面自动反馈检查、提交、充值中及最终结果；上游确认充值完成后，商城订单自动同步为 `completed`（已完成）。出现履约异常时，订单自动转入人工交付处理，向买家展示人工处理中，由运营核对后处理。

自动充值链路无需卡密或客服复制 Session。人工处理也不保存或展示 Session；如需再次检查凭据，由买家重新提交。

### 1.3 建议首期边界

- **购买范围：**只开放给主站已登录买家，每笔订单仅含一个直充规格、数量为 1，通过「立即购买」结算。
- **暂不开放：**游客、混合购物车、分销站、渠道 API 和下游站点；不改造已产生订单的旧商品，也不做自动退款。
- **商户付款：**首期建议用商户侧 `auto_card`，由运营配置可用的 `product_code`；`own_card` 留作后续能力。买家不选择或接触商户付款卡。
- **地区限制：**如果联调确认目标地区不支持该卡头，先停售对应规格。

## 2. 商品与动态 SKU

### 2.1 商品类型

在现有商品编辑弹窗与商品写入逻辑中增加独立的「Kafuda GPT Direct（直充）」选项，建议内部值 `fulfillment_type=kafuda_gpt_direct`。这是商品履约类型，和上游商户付款方式 `auto_card` / `own_card` 分别建模。

选中后展示目录同步、SKU 成本价、售价和启停控件，隐藏卡密导入、卡密库存、人工库存、库存展示配置和普通人工交付结算表单。不能因卡密数量为 0 而将直充 SKU 判为售罄；可售性由 SKU 配置、目录和运营开关决定。订单创建、取消、付款、退款均不执行卡密或人工库存预占、扣减、释放和回补。

切换类型时核查已有 SKU、卡密占用、上游映射与未完结订单，明确不兼容配置的处理提示，不自动删除已有卡密或改写历史订单快照。已产生订单继续按其原快照履约；本期不批量转换旧订单。异常转人工仅作用于对应订单的履约处理方式，不把商品或其他订单整体改为 `manual`。

正常直充单不能通过普通人工交付或通用改状态绕过上游确认。已进入人工处理的异常单，可经第 4.4 节的受控入口交付。

### 2.2 动态获取、站内定价

服务端调用 Kafuda `GET /api/v1/gpt/catalog`，用实际确认可售的「`plan` + `country`」作为同一商品下的规格键；不能仅凭套餐和地区列表做笛卡尔积。复用本地 SKU ID、规格和价格字段，另外保存明确的上游标识、目录可用状态。

新规格默认未完成价格配置、未启用；管理员按站内币种逐个自定义成本价与基础售价。复用 `ProductSKU.CostPriceAmount`（`cost_price_amount`）和 `PriceAmount`（`price_amount`），两项均由管理员维护，遵循现有金额精度与合法性校验。成本可显式配置为 0，不将缺失配置静默视为已确认；售价须满足现有可售校验。

区分三类金额：管理员成本价用于本地成本快照与利润口径；站内售价用于买家结算；上游报价和实际费用用于商户扣费及风控。上游约价只给运营参考，不能自动覆盖管理员成本价或售价，也不能直接替代 USD cents 的上游成本上限。实际扣费单独记录，不回写覆盖已下单的成本快照。成本、商户报价及实际费用仅对授权后台公开，买家接口和页面不得暴露。

首期沿用现有站内定价和支付校验，直充 SKU 的优惠配置须纳入上线检查。

### 2.3 同步规则

- 进入编辑页时读取最近一次有效目录，管理员可刷新。
- 按规格键合并，保留 SKU ID、管理员成本价、售价和手动启停；目录确认下架时停止新购，不删除 SKU；重新出现时保留两种价格，由管理员复核后重新开售。
- 目录请求失败或响应无效不覆盖上次有效数据；展示同步结果和时间，目录超过运营设定的有效期则暂停新购。
- 商品浏览和结算读取本地数据，预览与创建订单都重新校验可售性。

### 2.4 订单快照

创建订单时锁定本地 SKU、套餐、地区、管理员成本价、站内成交价及履约所需的付款配置标识（不含密钥）；复用订单项已有 `CostPrice` 成本快照，并检查买家响应的成本剥离逻辑。不接受买家在直充请求中覆盖这些字段。

后台修改成本价或售价、停售、刷新目录后，已付订单仍按快照处理；若上游已无法提供该规格，订单进入人工交付处理，不能悄悄换区、换套餐或补价。

### 2.5 前台展示

商品页显示套餐、地区、售价及「付款后提交 ChatGPT Session」提示。把锁区、已有订阅、半价资格或点数资格等限制说明放在购买前；具体账号资格以付款后检查为准。可售按本地启用、定价、目录状态判断，不显示卡密库存数量，也不承诺账号一定能开通。

## 3. 支付后直充

### 3.1 等待凭据

在线付款回调或钱包支付沿用商城现有逻辑。订单确认已付后，支付结果页引导到订单详情；详情区展示「待提交 Session」。未付、取消、已退款及非本人的订单不能提交；服务端校验用户、租户和实际履约子单。支付成功本身不调用 Kafuda，也不触发自动发卡、人工发货或现有上游采购。

### 3.2 提交一次，校验后直接下单

- 买家核对所需套餐、购买地区和要充值的账号，确认将凭据临时发送给 Kafuda 后点击「确认直充」。
- 接受完整的 ChatGPT 会话 JSON（含 `sessionToken`）或单独的 session token，不接受只有 Access Token 的输入。
- 服务端以订单快照的地区、`pay_mode` 和卡头调用 Kafuda `POST /api/v1/gpt/check`；只选与已购套餐相同、`available` 且未过期的一条报价。
- 同次检查的其他报价不用；锁区、已开通、无资格、暂不可买都不发起上游订单，说明原因并进入人工交付处理。Session 格式错误或明确失效等可更正输入允许用户重新填写；身份校验拒绝不改变订单状态。
- 报价有效期读 `expires_at`，不写死为九分钟。若检查回报的业务类型或费用超出商户允许范围，进入人工交付处理，商城不改变已付金额。

### 3.3 调用上游

调用 Kafuda `POST /api/v1/gpt/orders`，发送刚取得的 `quote_id` 与商户侧生成的唯一 `reference`，长度 1–80 字符。`auto_card` 用目录确认的卡头；后端按实际报价字段设 USD cents 的成本上限，包括开卡和充值成本；不直接用当地币金额与站内售价相减，也不直接把管理员填写的站内币种成本价当作上游限额。余额不足、卡头异常或超限时暂停本次提交，自动进入人工交付处理并提示运营。

### 3.4 查结果与实时进度反馈

受理后保存上游数字订单 ID。后台轮询 Kafuda `GET /api/v1/gpt/orders/{id}`，按接口建议的 5–10 秒起步，之后按限额、运行时长和错误退避；页面只读取站内状态。账单已付但上游未确认时保持处理中。

前台在订单详情自动轮询站内状态接口，展示「待提交 → 检查中 → 提交中 → 充值中 → 已完成 / 人工处理中」及最近更新时间，无需买家手动刷新。首期沿用站内鉴权请求与轮询方式，页面进入时立即拉取，离开时清理轮询，恢复页面时重新拉取；临时网络错误重试并提示同步延迟，不显示为充值失败。前后台都可看到最新的脱敏业务阶段。

进度仅展示接口确实可确认的阶段，不编造百分比、剩余时间或内部日志。上下游轮询周期分别配置并受限流约束，联调记录实际反馈延迟；这是近实时状态反馈。完成后停止页面轮询；人工处理中降低频率或按需刷新，结果不明时后台仍继续查证。页面离开不终止服务端履约任务。

上游确认 `completed` 后，幂等创建脱敏交付记录，履约状态记为已交付，实际履约订单状态直接同步为 `completed`（已完成）；存在父单时汇总更新父单，前台自动显示完成。不能只写成 `delivered` 后再等待人工完成。

回调有完整签名、重放防护、事件样例后再接入；校验通过的回调也走同一状态更新入口，必要时按订单 ID 主动查证。

### 3.5 直充状态与处理规则

| 直充子状态 | 处理规则 |
| --- | --- |
| 待提交 / 可更正 | 已付且无在途尝试；校验失败时显示可操作的提示。报价明确过期且确认未受理时，重新提交后获取新报价。 |
| 检查中 / 提交中 / 处理中 | 上游 `submitting`、`processing` 或站内正在处理；拒绝新增尝试，刷新页面可继续查看。 |
| 人工处理中 / 待核对 | 上游 `needs_review`，或提交超时等造成结果不明；自动进入人工队列并继续查单，必要时由运营用 `reference` 核对。禁止再次充值、人工标记完成和直接退款。进程重启本身优先恢复任务；恢复后仍无法确认结果才转待核对。 |
| 人工处理中 / 待人工交付 | 上游明确失败或取消、账号业务资格不符、费用超限等无法继续自动履约；记录脱敏原因。仅确认不会再自动开通且无在途尝试后，开放受控人工交付、重新提交或售后退款。 |
| 已开通 / 订单已完成 | 上游 `completed`；幂等落交付记录与时间，实际履约单设为 `completed` 并汇总父单，关闭该单人工待办。订单详情展示脱敏结果，不生成卡密文件；完成提醒不包含凭据。若接口返回 `renewal_cancelled`，按实际结果展示；点数不显示续费信息。 |
| 失败 / 已取消（上游尝试） | 上游尝试保留 `failed` 或 `cancelled` 结果；商城已付订单转人工交付处理，不因上游取消而改成未付或已退款。Kafuda 退商户服务费与商城买家退款是两笔业务。 |

### 3.6 异常转人工的状态语义

代码中的订单主状态（`paid`、`fulfilling`、`completed` 等）与交付类型（`auto`、`manual` 等）是两种概念，目前没有名为「人工交付」的订单主状态。本期须增加可持久化的订单人工接管标记 / 履约子状态，在前后台明确展示「人工处理中」，并支持后台筛选及待办；字段名称在 K02 规划时确定。

进入人工处理时，保留已付事实，未完成订单主状态使用 `fulfilling`，保留商品类型、原始订单快照、上游尝试和 reference；不能仅修改商品类型或显示文案来代替状态落库。人工处理原因区分「待核对」与「可人工交付」，异常发生后自动进入对应队列，不依赖用户主动联系客服。

普通查单的短暂网络失败按退避继续；达到配置的重试或处理时限后转人工待核对。结果不明转人工后继续上游查询；若随后确认成功，仍走统一幂等完成入口，并关闭人工交付操作。人工操作与上游结果更新使用相同订单锁，防止双方各交付一次。

### 4.2 凭据只用于当次请求

- 通过 HTTPS、带大小限制的 POST 请求体提交；前端仅置于表单内存，提交后清空。
- 后端只在检查/报价请求期间使用，不进人工表单、数据库、Redis、任务负载或重试队列；不进入 URL、日志、监控链路、埋点、错误报告及客服界面。
- 关闭该路由的请求体采集，也不透传上游原始错误或完整邮箱。订单仅公开脱敏账号与可公开状态。
- 对用户和订单限流；加载商户密钥使用部署侧敏感配置。

### 4.3 防重复充值

- 每个履约单任一时刻最多一个活跃尝试。先在短事务内锁定订单、核验可履约并持久化尝试号及唯一 `reference`；调用上游下单前先记录「可能已发出」，提交事务后才发请求。
- 并发点击、请求重放、进程重启和任务重投均复用已有记录。已知上游 ID 直接查单；拿不到 ID 时优先按 `reference` 查证。
- 只有上游明确支持安全重放且可复用原请求时，才用相同 `reference` 重放；不以新报价或新 reference 猜测重试。
- 若只有按数字 ID 查询且未收到 ID，转人工核对；联调须验证人工查单渠道，否则不得开放销售。

### 4.4 人工交付、退款与状态一致

- 直充异常自动持久化人工处理标记、脱敏原因和进入时间；后台可筛选待核对、待人工交付及已处理。保留原始直充快照，不全局修改商品类型，不丢失上游尝试。
- 仅已进入人工队列、确认上游不会再开通且无在途尝试的订单可人工交付。运营确认实际完成后，经受权限控制的入口记录脱敏交付结果和操作人；本期直充异常单人工交付后也进入 `completed`，不改变普通人工商品原有流程，不导入、预占或生成卡密。
- 如需恢复自动直充，由运营先核实并解除人工接管；买家重新提交 Session 后才可开启新尝试，不从任务或数据库中恢复旧凭据。待核对期间始终禁止重充。
- 提交、人工接管、人工交付、上游结果更新和退款使用同一订单锁并在事务内复核状态。已退款不允许提交；提交中、处理中与结果不明不允许退款；上游成功与商城退款不能互相覆盖。后台普通人工交付和通用状态更新入口同样执行这些约束，不能绕过专用界面限制。
- 确认未开通且无在途尝试后，由现有售后流程根据站内实付发起退款，不以 Kafuda 退费作为买家退款凭证。
- 回调、轮询及人工处理的同一结果只产生一次交付和完成通知；迟到的成功关闭人工待办，旧事件不能把已完成订单退回人工处理中。

### 4.5 任务及事务

- 协调状态与到期任务持久化；建议首期复用现有 Redis worker，并用周期扫描补偿漏入队和重启。任务只传本地记录 ID。
- 启用直充销售前检查 worker 已配置且运行，提供管理员按已知上游 ID 核对的入口，处理已付款订单。
- SQLite 事务内只用绑定 store，设置事务外预读，HTTP 调用全部在事务外；迁移及并发行为兼容 SQLite 和 PostgreSQL。

## 5. 开发任务卡

任务卡用于限定单次计划与开发范围，详细业务规则仍以第 1–4 节为准。每项完成时同时满足第 7 节中与本次改动相关的验证要求。

### K01 · 上游联调与前置确认

- **依赖：**无；需提供完整 Kafuda 接口说明、测试环境、测试账号及商户配置。密钥不得写入本文或仓库。
- **范围：**确认 API 地址、鉴权、`gpt` 权限、速率限制、错误结构、套餐与地区对应关系及卡头适用范围；核实 Session 输入格式、凭据保留约定、报价成本、进度字段、`reference` 去重与未知订单核对方式。完整问题见第 6.2 节。
- **交付：**在会话中列出已验证的响应字段、调用流程、核对渠道及剩余阻塞项，作为后续任务输入。
- **验收：**
  - [ ] 用测试环境走通目录、检查、报价、下单和按数字 ID 查单，确认可展示的真实充值阶段。
  - [ ] 验证未收到上游 ID 时的核对渠道，以及卡头地区适用范围和完整成本边界。
  - [ ] 尚未确认的语义明确列为阻塞项，未确认安全核对路径前不开放销售。

### K02 · 直充模块与持久化基础

- **依赖：**K01；模块命名、数据结构和配置落点先对照现有代码确定。
- **范围：**按模块分层封装 Kafuda client、目录缓存、尝试记录和结果同步；通过 `contract`、`internal/bootstrap/`、`internal/workflows/` 接入。持久化尝试号、唯一 `reference`、上游数字订单 ID、进度阶段、更新时间、人工接管标记、异常原因及到期任务；配置读取、事务和任务负载遵守第 4 节。
- **交付：**可供目录与履约任务复用的模块接口、存储和任务接入基础；不在本任务开放销售。
- **验收：**
  - [ ] 架构分层测试通过，迁移和存储兼容 SQLite、PostgreSQL。
  - [ ] 凭据不落库、不进入任务负载或重试队列；敏感配置不入仓库。
  - [ ] 设置在事务外预读，HTTP 在事务外执行，事务内查询只用绑定 store。

### K03 · 目录同步与后台商品配置

- **依赖：**K02。
- **范围：**落实第 2 节的 Direct 类型切换、真实可售组合、SKU 合并、自定义成本价与售价、启停、有效期及同步反馈；改造后台商品编辑弹窗及建议的目录读取、同步接口，隐藏并绕过卡密与人工库存配置。目录权限归 `operations`；商户凭据配置权限按 `integration` 管控。
- **交付：**管理员可切换 Direct 类型、同步目录、逐个设置成本价与售价并启用规格；补齐相关 API 与后台三语文案。
- **验收：**
  - [ ] 新规格默认未完成价格配置、未启用；同步保留 SKU ID、管理员成本价、售价和手动启停；类型切换不破坏历史订单或已有卡密。
  - [ ] 目录下架、重新出现、同步失败、无效响应和过期均按第 2 节处理。
  - [ ] 不生成未经确认的套餐与地区组合，不把上游约价自动写成成本价或售价；卡密库存为 0 不阻止已配置且目录可售的直充 SKU 销售。

### K04 · 购买限制与订单快照

- **依赖：**K03。
- **范围：**沿商品展示、订单预览、创建订单的调用链校验首期范围及可售性；封堵购物车、游客、分销站、渠道 API 和下游入口的绕过路径；锁定履约快照；检查直充 SKU 的优惠配置。
- **交付：**仅主站已登录买家可通过「立即购买」购买单一直充规格、数量 1；前端隐藏入口不能替代服务端校验。
- **验收：**
  - [ ] 预览和创建订单均校验本地启用、定价、目录状态及有效期。
  - [ ] 非支持入口、混合订单和错误数量均被服务端拒绝。
  - [ ] 成本和售价均快照；改价、停售和刷新目录不篡改已付订单；买家不能覆盖履约字段或读取成本。

### K05 · 支付后 Session 提交与上游下单

- **依赖：**K04。
- **范围：**核对在线支付和钱包付款调用链，支付成功后仅进入待提交；实现买家提交接口、身份与履约子单校验、凭据解析、账号检查、报价匹配、成本上限及上游下单；按第 4 节持久化防重复记录。
- **交付：**已付订单可按快照检查并下单；正常路径不触发现有发卡、普通人工交付或上游采购，业务异常按第 3 节转人工处理。
- **验收：**
  - [ ] 两种 Session 格式可处理；只有 Access Token、未付、取消、已退款、非本人及跨租户请求被拒绝。
  - [ ] 只使用已购套餐的可用且未过期报价；账号资格、商户余额、卡头、费用或业务类型异常转人工处理，不更改买家已付金额；可更正输入与越权请求按第 3.2 节处理。
  - [ ] 双击、重放和并发请求最多产生一个活跃尝试；调用前持久化「可能已发出」，结果不明不以新 reference 猜测重试。

### K06 · 进度同步、订单完成与异常转人工

- **依赖：**K05。
- **范围：**实现第 3 节的进度阶段、更新时间、轮询退避、到期任务、周期补偿及恢复；上游成功时交付并同步订单完成，异常时持久化人工处理及分类原因。首期采用轮询，回调留待协议完整后接入。
- **交付：**前台可读取最新站内阶段与人工处理状态；已知上游 ID 可查单，无 ID 的未知结果可按已验证渠道核对；迟到成功仍可安全完成。
- **验收：**
  - [ ] 上游 `completed` 幂等交付一次，本地履约单及父单同步 `completed`；不等待人工完成，不读取或生成卡密，乱序事件不倒退状态。
  - [ ] 受理后响应丢失、进程重启、任务重投和漏入队均可恢复或转待核对；未知结果不再下单。
  - [ ] `needs_review`、业务失败、取消及超限等自动进入人工队列；暂时查单失败按退避处理，超过设定时限转人工待核对；人工状态刷新后仍保留。
  - [ ] 结果不明继续查证，迟到成功关闭人工待办；只有确认尝试终结且不会开通才允许解除接管并重新提交。

### K07 · 人工交付、退款保护与后台售后

- **依赖：**K06。
- **范围：**接入受控人工交付、解除接管、钱包及人工退款入口；人工操作和上游同步共用订单锁并复核状态。后台展示尝试号、上游单号、脱敏账号、状态及错误分类，提供人工队列筛选、核对和交付操作，权限归 `support`。
- **交付：**运营可核对未知结果，并对已确认无在途履约的异常单人工交付或按站内实付退款；普通商品原有交付不变。
- **验收：**
  - [ ] 已退款不能提交；提交中、处理中和结果不明不能退款；上游成功与商城退款不能互相覆盖。
  - [ ] 确认未开通且无在途尝试后才可人工交付、解除接管或进入售后退款；待核对单的普通人工交付和通用状态入口同样被拒绝。
  - [ ] 人工交付成功后直充订单同步 `completed`，保留来源与操作人；与迟到成功并发时不重复交付、不重复通知、不倒退状态。
  - [ ] 后台不展示凭据、完整邮箱或上游原始错误；Kafuda 退费不作为买家退款凭证。

### K08 · 前台购买与实时进度页面

- **依赖：**K04、K05、K06、K07；依赖接口可用后验收完整链路。

  - [ ] 无需手动刷新即可看到最新阶段、完成与人工处理；离页清理轮询，回页恢复同步，断网不误报业务失败，完成后停止轮询；不展示虚构百分比。
  - [ ] Session 仅保留在表单内存，提交后清空，不进入浏览器持久存储、URL、埋点和错误报告。
  - [ ] 不显示卡密库存或承诺一定开通；按实际结果展示续费信息，点数不展示续费信息。

## 6. 排期与联调阻塞项

### 6.1 原始排期参考

以下是完整功能的人日估算，不是单次会话时限；任务卡进一步拆分了这些阶段，不重复累加估时。

| 阶段 | 工作与交付 | 预计 |
| --- | --- | --- |
| 1. 上游联调（K01） | 确认 API 地址、鉴权与 `gpt` 权限、目录实际响应和卡头地区适用范围；拿到测试账号与商户配置，验证报价、下单及按 reference 核对的路径。 | 1–2 人日 |
| 2. 商品与结算（K02–K04） | 完成类型切换、目录缓存及合并、自定义成本价与售价、无库存购买校验、订单快照和主站单品购买限制。 | 2–3 人日 |
| 3. 履约与售后（K05–K08） | 完成提交、幂等、轮询、页面进度反馈、自动完成、异常转人工及受控人工交付，以及权限和退款并发保护。 | 3–4 人日 |
| 4. 联测与灰度（K09–K10） | 覆盖两个店面模板、两种数据库及支付方式；先用一个已验证的套餐和地区小范围开放，核对实付、上游费用、开通结果和凭据清理。 | 2–3 人日 |

原估算合计 **8–12 人日**，以测试环境可用、上游鉴权和核对路径已确认、首期仅轮询为前提；本次补齐成本价维护、自动进度和人工接管闭环后，须在相应任务规划时重新核定工期，该区间不作为交付承诺。回调可后续补齐；凭据处理、商户成本及上游结果不明时的核对路径须在上线前验证。关闭销售开关时只阻断新购，保留已付订单提交、查单及人工交付 / 售后入口，并保留已有 SKU 和订单记录。

### 6.2 联调时需要供应商确认

- [ ] 目录套餐与地区的确切对应结构，以及卡头的地区适用范围。
- [ ] 账号凭据保留和删除约定。
- [ ] 支持的 Session 输入结构、检查与下单时凭据或报价的实际传递约定；本文字段在完整文档和联调中复核，不凭旧片段定实现。
- [ ] API Token 权限、速率限制与错误结构。
- [ ] 订单可返回的充值阶段、更新时间、终态语义，以及允许的轮询频率；确认可反馈的进度粒度及实际延迟。
- [ ] `reference` 去重作用域和保留时长、未知订单查证方式及人工核对渠道。
- [ ] 报价里 `auto_card.total_cents` 的完整成本边界，以及失败、取消时开卡费和卡余额如何处理。
- [ ] 回调的签名、重放防护、事件字段、样例和重试策略；不从现有片段推断，首期轮询不依赖回调开放。

## 7. 交付验证与上线验收

### 7.1 业务验收矩阵

- [ ] **类型、目录与价格（K03、K04）：**后台可切换 Direct 类型；SKU 来自动态目录，两种价格可自定义；目录新增规格不会直接开卖；刷新不丢成本价和售价；下架不能新购；同步失败不误删；改价和停卖不篡改已付订单，成本及上游费用不暴露给买家。
- [ ] **无库存副作用（K03–K07、K09）：**卡密数量为 0 仍可购买已配置且目录可售的直充 SKU；创建、付款、取消、退款和人工接管均不查询、预占、扣减、释放或回补卡密及人工库存，不保存普通人工结算表单，不生成卡密下载；普通卡密、人工和现有上游商品照常交付。
- [ ] **支付与页面（K05、K08）：**付款前看不到表单且请求被服务端拒绝；线上和钱包付款后，两个模板都可从支付结果和订单详情进入直充。商品切换类型不破坏旧订单及原库存归属。
- [ ] **自动进度与完成（K06、K08）：**两个模板均自动显示真实阶段、更新时间、最终完成或人工处理；刷新与离页重返可恢复；网络故障只提示同步延迟；上游 `completed` 后履约单与父单同步完成，不依赖手动刷新或管理员确认。
- [ ] **异常转人工（K06、K07、K08）：**业务拒绝、余额或成本异常、上游失败 / 取消及结果不明均按分类进入持久化人工队列；前后台可见并支持后台筛选。结果不明时继续查证，禁止重充、人工完成和退款；确认无在途履约后可受控人工交付或售后，人工完成后直充订单也同步 `completed`。
- [ ] **凭据、报价与越权（K05、K09）：**两种 Session 格式通过规格匹配后可实际开通；只有 Access Token、失效凭据、锁区、无资格、过期报价等均有明确提示，且不会下错套餐、不产生重复充值。测试跨账号、跨租户、未支持渠道的越权请求；检查敏感数据未出现在浏览器持久存储、数据库、日志、任务和错误报告中。
- [ ] **并发与恢复（K05–K07、K09、K10）：**测试双击、并发请求、上游已受理但响应丢失、进程重启、查单乱序、退款并发、上游拒绝和长时间待核对；补测人工处理中迟到成功、人工交付与上游同时更新、普通状态接口绕过。成功只交付并通知一次，旧事件不倒退，未知状态不会再下单或触发退款。验证停卖后仍能处理旧单。
